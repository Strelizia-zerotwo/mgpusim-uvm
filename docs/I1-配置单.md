# I-1 修复变体与理想选择：v3

所有变体使用 `INV-配置单.md` 相同的所有者放置、映射准备、缓存屏障、固定服务和链路参数。

| 名称 | 需要修复时的行为 | 对照含义 |
| --- | --- | --- |
| i1 | 只修本阶段要读、且已过期的子块 | 原按需差量策略，可能重复支付服务 |
| i1-full-stale | 本阶段需要修复时，一次补齐该副本所有过期子块 | 避免连续读取不同旧子块导致多次修复 |
| i1-adaptive | 比较按需与全过期补齐的前视成本，选择较便宜者 | per-copy oracle前视启发式；不是端到端最优证明 |
| i1-write-prefetch | 独立允许写阶段冷副本 | 额外策略，不混入前三种策略的S3 |
| oracle-envelope | 对已实际回放的INV及前三种策略，取整次应用总时间最小者 | 包含INV兜底，保证该候选集合的报告时间不高于INV |

前三种策略均只在写阶段继续使用“阶段开始前已有、且所需子块已经有效”的副本；不在写阶段新建冷副本或修复已有过期目标。写阶段新增副本、字节、固定服务、读取四项必须为0。

全过期补齐也不会在“本阶段所读子块已经干净”时凭空触发修复。冷的首次复制仍为整页。

## 前视选择具体计算什么

从当前副本有效位出发，查看当前页下一次写入之前、同一GPU未来各阶段要读取的子块。模拟按需修复是否会重复触发事件，再比较：固定服务+附加传播+有效载荷和每连续区间16 B头部的独立传输成本。传输按配置粒度取整。

该比较有真实代价依据，但没有预测所有GPU的共享链路排队、服务槽重叠和后续写入后的所有分支，因此**局部选择不能保证整机时间不慢于INV**。不能仅把“本次复制字节较少”称为上界。

## 严格不劣于INV的报告口径

run.py保存 `oracle-envelope.json/tsv`：每个link/fault/repeat配置，从真实、完整、已校验的INV / i1 / i1-full-stale / i1-adaptive回放中选最短者。输出selected_policy、selected_case和候选列表，INV本身就是可选项。

这是**整次应用的理想策略选择包络**，不拼接不同回放的kernel片段，不把每个事件的局部最小值冒充真实总时间。它只保证候选集合内的时间≤INV，不等于已经实现一个可在线获得全部收益的硬件机制，也不是穷尽所有逐次修复决策的全局最优。

```bash
cd /home/only/projects/mgpusim-uvm
python3 benchmark/replica-recovery/run.py \
  --workload parallel-stencil   \
  --size 258 \
  --columns 258 \
  --iterations 4 \
  --home-placement owner   \
  --policies norep,inv,i1,i1-full-stale,i1-adaptive   \
  --link-ns 0,200 \
  --fault-ns 900,20000
```

当前所有者布局中，写阶段S3计数为0；它用于回答halo复制成本和修复策略问题。元数据维护、目录查找、PTE安装和shootdown免费，INV享有相同理想化。公共全量缓存屏障仍计费。i2仍仅为参数化成本预算，没有真实元数据记录硬件。
